# Contributing to Basira

Thanks for thinking about contributing. Basira is small and opinionated —
please read this before opening a PR, it'll save us both time.

## Local setup

You need:
- Docker + Docker Compose
- A GitHub account (to register your own dev App)
- An Anthropic API key

```bash
git clone https://github.com/2lba/basira.git
cd basira
cp .env.example .env
# fill in: SECRET_KEY, TOKEN_ENCRYPTION_KEY, ANTHROPIC_API_KEY,
#         GITHUB_APP_* (see README for App setup)
docker compose up -d
```

The backend container runs `alembic upgrade head` on every boot, so a
fresh clone + `docker compose up` should land you at a working API on
http://localhost:8001 and a frontend on http://localhost:5173.

## Running tests

```bash
# backend
docker compose exec backend pytest tests/ -q
docker compose exec backend ruff check app/

# frontend
docker compose exec frontend npx eslint src/ --ext .js,.jsx

# end-to-end (browser)
docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d
cd frontend/e2e
npm install
npx playwright test
```

All three should be green before you open a PR.

## Coding standards

**Python**
- Black + Ruff. `docker compose exec backend black app/ tests/` and
  `ruff check app/ --fix` keep things tidy.
- Type hints on public functions. Internal helpers can skip them if the
  intent is obvious.
- No `print` calls in `app/` — use the structlog logger.

**JavaScript / React**
- ESLint flat config (`eslint.config.js`). Run `npx eslint src/` before
  pushing.
- Function components with hooks. No class components.
- Tailwind utility classes. Don't introduce new global CSS.

**No emoji in code, commits, or docs** (yes, even the funny ones). Basira
follows the CLAUDE.md house style: short, lowercase commit messages, no
"feat:" / "chore:" prefixes, no AI-sounding marketing language.

## Commit messages

- Lowercase, present tense, ≤ 60 chars
- One concept per commit
- Examples:
  - `fix install url`
  - `harden webhook signature check`
  - `bump pyjwt to 2.12.0`
- **Don't** write conventional-commit prefixes (`feat:`, `chore:`, etc.).
- **Don't** include "generated by Claude" or "Co-Authored-By: an AI".

## PR process

1. Open an issue first for anything bigger than a small bug fix.
2. Branch off `main`. Keep the branch focused on one thing.
3. Write a test for any code you change. Tests must pass locally.
4. PR description: what changed, why, and any tradeoffs you're aware of.
5. CI must be green: backend tests, frontend lint, Playwright, pip-audit,
   npm audit, CodeQL.
6. One reviewer signs off. Reviewer squashes if the branch is messy.

## Where to look

- Backend routes: `backend/app/api/routes/`
- Scan engine + Claude prompts: `backend/app/services/scan_engine.py` and
  `scan_prompt.py`
- Webhook handling: `backend/app/services/webhooks.py`
- Frontend pages: `frontend/src/pages/`
- Threat model and security docs: `docs/security/`

## Style of disagreement

If you think a code change is wrong, say so directly. Don't pad with
"perhaps maybe we could think about" — review is feedback, not therapy.
If you disagree with a reviewer, push back; if you change your mind,
say so. The honest version wins.
